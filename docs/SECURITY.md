# Security

Cubex is a desktop client that holds API keys, reads and edits your files, and runs commands on a model's behalf. This page lists what protects you, and states plainly what it does not cover.

## Credential storage

- Secrets are encrypted with the operating system's credential store through Electron `safeStorage` (DPAPI on Windows, Keychain on macOS, libsecret on Linux). The encrypted values are kept in `credentials.enc.json` in the data folder, and the file is written atomically.
- A provider's saved configuration holds only an opaque `credentialRef`, never the key. The plaintext key is never written to `config.json` or the database. Deleting a provider deletes its stored secret.
- If operating-system encryption is unavailable (some Linux setups without a keyring), Cubex refuses to store a secret in plaintext and says so. You can supply keys through environment variables instead (`CUBEX_OPENAI_API_KEY`, `CUBEX_ANTHROPIC_API_KEY`, `CUBEX_GEMINI_API_KEY`, `CUBEX_OPENAI_COMPAT_API_KEY`), which are read only when no stored key exists for that kind of provider.
- A secret variable on an MCP server entry is stored the same way, under a reference Cubex derives from the server and variable names. A settings file cannot point a server at another credential.
- Shell commands, hooks and MCP servers start with a cleaned environment: variables whose names look like credentials (`CUBEX_*`, `*_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_PAT`, `*_CREDENTIAL`, `DATABASE_URL`, `ANTHROPIC_*`, `OPENAI_*`) are not passed on. A key a tool needs must be set on its own entry, such as an MCP server's environment variables.

## Secret redaction

Logs, error messages and the request inspector pass through the redaction helpers in `packages/core/src/redaction`. Values under keys such as `authorization`, `api-key`, `x-api-key`, `cookie`, `token`, `secret`, `password` and `credential` are replaced. Text that looks like a secret is scrubbed wherever it appears: OpenAI-style `sk-` keys, `sk-ant-` keys, `Bearer` tokens, GitHub `ghp_` tokens, Hugging Face `hf_` tokens and Google `AIza` keys. Output captured from hooks and MCP servers is redacted too, and an MCP server's own secret values are scrubbed from whatever it prints.

This is not a promise that arbitrary content is scrubbed. Source files, chat text and command output are shown as task data and may contain secrets.

## Electron hardening

- `contextIsolation` is on, `nodeIntegration` is off and the renderer is sandboxed. It has no Node access and reaches the main process only through the typed `window.cubex` bridge. Every handler treats its arguments as untrusted and validates ids, paths and sizes.
- A Content-Security-Policy limits the renderer to its own origin. Requests for `file:` URLs outside the renderer bundle are cancelled, so markup in a model reply cannot reach a network share or an arbitrary local file.
- Camera, microphone, location, notification and similar permission requests from the page are denied. Only writing to the clipboard is allowed.
- Links open in the system browser only for `http`, `https` and `mailto`. Navigating the window away from the app is blocked, and new windows are denied.
- Developer tools are disabled in the packaged app, and so are reload shortcuts. The packaged app allows one running instance.
- On Windows, Cubex sets `NoDefaultCurrentDirectoryInExePath` so that a program placed in a project folder cannot replace `git` or another tool that Cubex starts.
- Native modules are unpacked from the app archive (`asarUnpack: **/*.node`).

## Tool permissions

Every tool has a default permission of allow, ask or deny, and the mode you choose (Ask before edits, Accept edits, Plan mode or Bypass permissions) decides which asks are skipped. [HARNESS_WORKFLOW.md](HARNESS_WORKFLOW.md#permission-modes) has the full table. The points that matter for security:

- Plan mode blocks everything that would change something. Writes to protected folders (`.git`, `.cubex`, `.claude`, `.agents`, `.codex`, `.vscode`, `.husky`) ask in every mode except Bypass. A call recovered from model text instead of arriving as a real tool call always asks, even in Bypass.
- File tools reject paths that leave the project folder, including through symbolic links and junctions, and on Windows paths spelled in ways the file system would read differently. A file must have been read in the current turn before it is changed, and a change is refused if the file changed after that read. Searches skip symbolic links.
- `web_fetch` only reaches public addresses. It rejects private, loopback and link-local ranges, checks the address it actually connects to on each redirect, rejects URLs with embedded credentials, and asks before contacting a host that is not on a short list of documentation sites.
- The research subagent has a fixed read-only toolset. It cannot edit files, run commands, use the network, ask you questions or start another subagent.
- "Always allow" rules are created only from an ask Cubex raised, matched against the live call each time, and never offered for deletions, shells, interpreters, network tools, commands with shell syntax or calls carrying a risk notice.
- Approval does not override the operating system. An access-denied result is reported, and the model is told not to retry unchanged or switch shells to avoid it.

## What is not sandboxed

Cubex does not isolate commands, hooks or MCP servers. `run_command`, hooks, a goal's check command, MCP server processes, the programs you add as other agents and the commands an agent runs for a task you handed it run under your operating-system account, with your files and your network access. Permission modes decide when Cubex asks, but a command you approve can do anything you can. A hook runs a command on every matching event without asking, including in Bypass mode, and a goal's check command runs after every turn of the goal without asking, for the same reason. A background task keeps running until it ends or is stopped. Review what you approve, keep Plan mode and Ask before edits for work you do not yet trust, and treat MCP servers, hooks, check commands and other-agent programs as code you are choosing to run.

Local-only mode (below) is a model-routing setting. It is not a network firewall.

## Data on disk

Conversations, plans, review copies, command output and settings live in the data folder and are not encrypted by Cubex. Credential encryption is separate. A command's text and output can contain source code, personal data or secrets printed by the command, and these logs are not redacted like request diagnostics.

- Saved command output is limited to 2 MiB per command and 50 outputs per task, stored under generated ids in task-hashed folders, read only through bounded checked reads, and only by the task that owns it.
- The review panel keeps copies of the original files a task changed, up to 5 MiB per file and 64 MiB per task.
- Message display metadata is limited to 1 MiB and 128 blocks per message, and the complete message text is stored separately. Imported transcript data cannot reach another task's saved output and is never replayed as tool calls.
- Drafts and file checkpoints stay in memory and are gone after a restart.
- Logs are kept locally (turn them off with **Local logging** in Settings) and are redacted before they are written.

## Provider access

Provider adapters use each vendor's documented API or SDK. They do not scrape web interfaces, reuse session cookies, reverse-engineer private endpoints, or get around rate limits or subscription terms. A consumer subscription is not treated as API access: when a service offers no official third-party access, Cubex says so and stops. Other agents are a different case. Cubex starts the vendor's own program, which uses the login it saved itself, so a subscription is used only by the vendor's own software. Cubex never reads, copies, stores or sends that login, and it keeps anything that looks like a key out of the program's environment (see [Credential storage](#credential-storage)). Whether a subscription may be used through another program is the vendor's rule, and Cubex cannot check it.

## Updates

Cubex looks for a newer release of itself, downloads the installer and runs it when you say so. [UPDATES.md](UPDATES.md) has the whole story. What matters for security:

- The only request is a `GET` to `https://api.github.com/repos/HeshamXOR/Cubex/releases/latest`, with an `Accept` header, an API version header and `User-Agent: Cubex/<version>`. No cookie, token or identifier goes with it. It runs about every six hours, can be switched off, and is blocked by local-only mode.
- The release is untrusted text. Its tag must be a version. Its page and installer addresses are parsed and must be on `github.com` under the Cubex repository, with no user name in them. The installer must be the asset named exactly `Cubex-Setup-<version>.exe`, fully uploaded, up to 500 MiB, with a `sha256:` checksum that GitHub recorded. Without those Cubex still shows the release but will not install it.
- A download follows GitHub's redirects one step at a time, over `https`, only to `github.com` or `*.githubusercontent.com`, and at most five. Anything else stops it before it is requested.
- The size and SHA-256 are checked as the file arrives and again right before it is run. A file that fails is deleted. The path that is run is the file Cubex saved in its own data folder, never an address or a path that the release or the window supplied. The window can only ask for the next step, skip a version, or force a restart.
- The installer runs as a separate process with fixed arguments (`--updated /S --force-run`), under your account, without elevation, and only from a copy that the Windows installer set up. Cubex quits only after the installer has started.
- `CUBEX_UPDATE_FEED` points a development copy at a feed on the same computer. It takes only an `http` or `https` address on `127.0.0.1`, `localhost` or `[::1]`, so it cannot send a copy to another machine. Anything else leaves GitHub in place.
- The installer is not code-signed. The checksum comes from GitHub, so it protects against a damaged or swapped download and not against a release published by someone who controls the repository or its account. Whoever can publish a release in the repository can publish an update, so protect that account (two-factor sign-in) and, if you can, who may create release tags. Cubex 0.1.0 has no updater and is not affected.

## Other agents

The model can send a message to another agent you set up, or hand it a whole task: a program on this PC, which can be an agent that speaks the Agent Client Protocol (ACP), or a model of one of your providers ([OTHER_AGENTS.md](OTHER_AGENTS.md)). A message or a task leaves for another program or service, and it can carry your code.

- Cubex shows you the whole message and the agent's name and asks before the first message to each agent in a reply. Bypass permissions mode approves it without asking. A saved "Always allow" rule never covers it.
- A program is started without a shell, from the lookup that MCP servers use (the `PATH`, with the usual places where installers put command line tools added at the end, and never the working directory), with the cleaned environment described under [Credential storage](#credential-storage) plus only the variables you name under "Variables to pass". It starts in an empty folder that Cubex creates and deletes, so it sees only the message. Claude Code can be allowed to read the open project with `Read`, `Grep` and `Glob` only, with project settings and MCP servers off and nothing saved. It never gets `--dangerously-skip-permissions`. A custom program has no such limits: it runs as you, so treat it as code you choose to run.
- An ACP agent is started the same way, in an empty folder or, when you allow it, in the project folder. Cubex offers it no file access, no terminal and none of your MCP servers. When one of its tools asks for permission, Cubex answers by one rule: reading, searching and thinking are allowed inside the folder the agent was started in, with the path resolved through links first so that one leading out is refused, and every other kind of tool, and anything Cubex does not recognise, is refused. The answer is an option the agent itself offered, "once" and never "always", so nothing is written into the agent's own settings. Cubex moves the agent into its most careful mode, never into one it cannot read the meaning of or one that acts without asking, and refuses an agent that is in such a mode with no careful one to move to. An agent that moves itself into one mid-talk has its reply thrown away. All of this covers what an agent asks about. It can still do what it never asks about, so an ACP agent is a program you choose to run, like any other. Its session stays open between messages and is stopped after ten quiet minutes, when its settings change, when it fails, when the chat is deleted and when Cubex quits.
- What an agent answers is untrusted. It is bounded (400,000 characters of output, ten minutes), stripped of control sequences, scrubbed of anything shaped like a key, wrapped so it cannot close its own wrapper, and returned to the model as another agent's opinion and not as an instruction. It cannot approve anything: every tool call the model makes afterwards goes through the same permission checks as any other.
- Local-only mode does not start programs, ACP agents and tasks included, because nearly all of them reach a cloud service. A model agent follows the rule for providers.
- **Tasks.** An ACP agent with **Let it take on tasks** on gives the model `delegate_task`, and a task can change the project, so it is held to more than a message is:
  - Cubex shows you the whole task and the command that will be started and asks before every task. Bypass permissions mode approves it without asking. Accept edits mode still asks, and a saved "Always allow" rule never covers a task. Plan mode refuses a task that would change anything and asks about one that only reads.
  - Each task starts a fresh copy of the agent in the project folder, with no file access, no terminal and none of your MCP servers from Cubex, and the copy ends with the task. The agent works with its own tools.
  - When one of those tools needs permission, Cubex answers by the permission mode of the chat at that moment, the same way it does for its own tools. Reading is allowed inside the project and refused outside it. An edit, a delete or a move must name where, and where must be inside the project, in every mode: a request that names no place is never allowed without asking, and one that names a place outside the project is refused. Paths are resolved through links first, so a link cannot make something outside the project look inside. A protected folder (`.git`, `.cubex`, `.claude`, `.agents`, `.codex`, `.vscode`, `.husky`) asks in every mode except Bypass. A command asks unless it only looks or the mode is Bypass, and the question says that Cubex cannot limit what a command touches. Changing the agent's mode is always refused. A task that only reads (research, review) is refused everything but reading and a fetch you allow.
  - The answer is an option the agent itself offered, "once" and never "always". An agent that offers modes but none that asks before it changes things cannot be held to your permission mode, so it is given only tasks that read. **Test** says which kind an agent is.
  - Cubex lists the project folder before and after a task (at most 20,000 files and four seconds) and shows every file that differs, because an agent can change what it never asked about. A change it asked about is kept as it was for **Changes** and **Rewind**. A change it did not ask about is marked as not kept and cannot be rewound.
  - The agent's report is untrusted, like any other agent's answer: it is wrapped as another agent's account, and the model is told to read what changed and run the checks before it says the work is done. It cannot approve anything.
  - What a task runs on is the agent's own service and account. It does not count toward the spending limits in Cubex.
- **Found on this PC.** Settings looks for the coding agents Cubex knows by name. It finds each program the way a terminal would, never in the project folder, starts it with `--version` and, for Claude Code and Codex, with the command that prints who is signed in (`claude auth status`, `codex login status`). The programs start in the system's temporary folder, without a shell, with the cleaned environment, are stopped after six seconds (fifteen for the account command), and at most four run at once. What they print is cleaned and read as data, and the saved login is never read. In local-only mode the programs are looked for and not started. **Sign in** opens a terminal window that runs a sign-in command from Cubex's own list, with the program it found, and only on Windows. Cubex does not see what is typed in that window.
- **The Claude desktop app.** Claude Code is also looked for in the folders the Claude desktop app keeps its own copy in (`claude-code/<version>`, under `Claude` and `Claude-3p`). Cubex lists the folder names and checks that `claude.exe` is a file. It opens no other file there, because the app keeps its login nearby. The copy it finds is started as it is and never changed, moved or updated, and its own self-update is switched off for the run.
- **Claude Code, started directly.** The connection called `claude-direct` starts Claude Code in its `stream-json` mode with `--permission-prompt-tool stdio`, so it asks Cubex before every tool it uses. The answer is the chat's permission mode applied by the same policy as for any other agent, once and never "always". The tools it has at all are named with `--tools`: the ones that read for an opinion, and the ones that change things or reach out too for a task. Your own Claude Code settings are loaded for the sign-in and the model and the project's never are, and a settings file of Cubex's goes on top: every tool that reads, changes or reaches out is "ask", hooks are off, the mode that never asks cannot be entered, and no "co-authored by" line is added. Your MCP servers are not loaded and nothing is saved to disk. A tool that changes something and runs without asking ends the turn and the program, because the question was the only thing that held it to the policy. Claude Code was tried this way against the real program, with a stand-in for the model service.
- **Antigravity.** Google's agent runtime is a download, so it gets more care than a program that is already installed:
  - It is downloaded only when you choose **Install the runtime**, from `dl.google.com` over HTTPS. Nothing from the download is run until it matches what Cubex pins: the size and the SHA-256 of the archive, the two programs in it by name and size (the archive reader refuses anything else: a name with a path, encryption, a compression method it has no use for, more than one disk), and a handshake in which the program says it is that release. Until then, what was installed before stays the active one. A wrong number in Cubex makes an install fail and never makes it unsafe. Cubex does not redistribute the runtime.
  - It runs with a profile of its own in Cubex's data folder and a temporary folder for each run. The variables that would point it at another login, or move its profile, are removed from its environment (`GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, the Google Cloud project settings, `GEMINI_HOME`, `BROWSER` and the like). It does not use `~/.gemini`, and Cubex never starts or reads the Antigravity desktop app.
  - Signing in is your own action in Settings and never something a chat does. The runtime reports the address of Google's sign-in page through a small helper that Cubex sets as its `BROWSER`, and Cubex opens the address only when it is `https://accounts.google.com/o/oauth2/v2/auth` and sends the answer back to `http://127.0.0.1:<port>/`. Any other address is refused: nothing is opened and the sign-in fails at once. Google's answer goes straight to the runtime on this PC, so Cubex never sees the page, the code or the token. It never opens the file where the runtime saves the sign-in and only asks whether it is there. **Sign out** asks the runtime to forget the sign-in, and **Remove** deletes the profile with the runtime.
  - The runtime is never allowed to ask for a sign-in inside a chat. A filter between Cubex and the runtime fails the request with "not signed in" and stops the runtime. The same filter answers the runtime's questions for the person, which it sends in the place of permission requests, with "cancelled", because choosing one of their answers would be speaking for you. Its real permission requests go through the same policy as every other ACP agent's, and its tool calls are bounded and put in the shape the rest of Cubex reads.
  - Install, sign-in, sign-out and starting the runtime are all off in local-only mode. A runtime that is running holds its release in place, and **Remove** stops the sessions that chats keep open and says to stop a running task first.
  - The runtime is Google's software, under Google's terms. It was tried in the packaged app with a stand-in that speaks its protocol, and not yet with the real runtime.
- The **Test** button in Settings starts a real program or sends a real request. At most two run at once, and the main process checks the agent the way it checks one that is saved.

## Goals

A goal keeps the agent working across turns without a message from you each time ([HARNESS_WORKFLOW.md](HARNESS_WORKFLOW.md#goals)). What matters for security:

- A goal does not change what the agent may do. Every tool call in a goal's turn goes through the same permission checks as in any other turn, and a turn that waits for your answer holds the goal until you give it. In Bypass permissions mode there is nothing to wait for, so a goal can run its 15 turns of tool calls unattended, and **Keep going** allows 15 more. Keep goals for projects you can restore, and use the review panel afterwards.
- The check command is typed by you, with the goal, and only the `/goal` command in the composer can set it. The agent cannot change which command runs. It runs in the project folder, under your account, with Cubex's own credentials kept out of its environment, and it and everything it started are stopped after ten minutes or when you pause the goal. What it proves is limited to what it tests: an agent that edits the tests can make a check pass, so read the **Changes** tab.
- Without a check command, the agent's word that the goal is met is evidence for a model to weigh, not a verdict. That model sees the goal, the agent's note and a record of the turn, which can include text from files and web pages, and it is told to treat all of it as data. The reason it gives for "not met" goes to the agent in a message from Cubex, so text that sways the judge can steer the agent a little, and no further than the permission checks allow.
- Judging without a check command is one more request to the task's own model, billed and counted like any other. A spending cap that is set to Stop is checked before it is made, and a goal stops when one has been reached.

## Privacy

- Cubex sends no telemetry and has no analytics. The `telemetry` flag in the settings schema is not read by any code.
- Network traffic comes from what you configure and use: requests to your model providers, `web_search` (which sends the query to DuckDuckGo's HTML search page), `web_fetch` pages, the Ollama registry lookup that sizes a download, the model catalog at `https://models.dev/api.json` (downloaded at most every six hours, carrying nothing about you, cached on disk, and never called in local-only mode), the update check described above, and whatever your MCP servers, hooks, goal check commands, shell commands and other agents do. A program you add as another agent may send a message or a task on to its own service, and one that runs through `npx` downloads its adapter from npm the first time. Looking for the agents on this PC under **Found on this PC** starts each program with `--version`, and the program may contact its own service as it does when you run it.
- **Local-only mode** is checked before every model request, retry and fallback, including for a provider that was already created. It also blocks model-list refreshes and connection tests for cloud providers. Turning it on does not stop requests already in flight. The offline demo, Ollama, LM Studio and llama.cpp stay available, and a custom or OpenAI-compatible endpoint stays available only if you declare it local. Azure OpenAI and the native OpenAI, Anthropic and Gemini adapters are always treated as cloud, whatever they are labelled. A local declaration is trusted configuration, not an address check, so a remote address labelled local passes. The setting does not restrict tools, hooks, model downloads, MCP servers or child processes. It does block Cubex's own update checks and downloads and the model catalog download, and it keeps Cubex from starting other agents that are programs, ACP agents and tasks included.
- Tool results and recovered command output that the model asks for are sent to the active provider as part of the conversation, under that provider's terms.

## Reporting a vulnerability

Please report security issues privately, using GitHub's "Report a vulnerability" option on the repository's Security tab, and not in a public issue. Include steps to reproduce and the versions affected. We will acknowledge the report and agree a timeline for a fix and disclosure with you.
